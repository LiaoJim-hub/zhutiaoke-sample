## 一、它不解决什么（先读这一段）

- **它不判断内容对不对。** 它只判断"这份文件与它自带的指纹值是否一致"。
- **它不证明"没被改过"。** ★ 指纹内嵌在被校验的同一份文件里：改正文 → 重算 → 改写指纹行 ⇒ **照样一致**。要防"改完再重签"，必须用**外部锚**（见 §六）。
- **它不是认证。** 一致不等于合规、不等于合格、不等于监管认可。
- **它不背书。** 我们不出具人、不签字、不替你承担责任。
- **它不做排行。** 不存在分数、等级、名次。
- **它不是审计报告。** 样例报告**不供签署**，**不得用于对外质证 / 诉讼 / 向监管提交**——那一档须由具备资质的主体出具。
- **「未问」≠「通过」。** 材料里没呈现、或判据不适用的，记 **判不了（uncomputable）**，不记为绿。

> 一句话：**它能证明"字与签名对得上"，不能证明"话说得对"，也不能单独证明"没被改过"。**

## 三、这份样例怎么读（底稿三查）

样例对象是一份**合成**的审计工作底稿节选（某有限责任公司 2025 年度财务报表审计）。报告结论是 **2 红 + 1 判不了**：

| 判据 | 结论 | 红在哪 / 为什么判不了 |
|---|---|---|
| `wp_three_tables` | 红 | 三张表的**复核底稿均未见**（本判据查三张表；财政部该决定书**第六项**针对的是**合并现金流量表**这一张） |
| `wp_confirm_transit` | 红 | 函证**回函经被审计单位转交** ⇒ 回函可靠性未评估、证据链断裂（对应决定书**第八项**） |
| `wp_key_audit_matters` | **判不了（不适用）** | 材料同时含「底稿目录」与「报告节选」⇒ 该段是否本应存在无法判定；且主体为**非上市**有限责任公司，准则第 1504 号对关键审计事项段的强制要求针对上市实体 |

> 两条红的出处是**监管处罚认定**，不是我们编的规矩：
> 财政部《行政处罚决定书》**财监法〔2025〕371 号**（2025-12-29）。
> ★ 该决定书正文按「一、…八、」分项，本报告引用的项号即此口径（第六项、第八项）。

**只判这三条，不判更多。** 我们明确不判：底稿是否"编造"、合并抵销对不对、审计结论对不对——那要交叉验证物流/银行流水/两套数，或职业判断，**不是纯文本能判的**。报告「三、这份报告不做什么」逐条写了为什么。

**判据集本身不在本仓库。** 报告只给一个判据版本值（`workpaper:…`），**该值在本仓库无法复算**，仅用于产品内比对"是不是同一版判据跑的"。

**样例材料是合成的**（不是"真实底稿脱敏"）：事实要素取自上述公开决定书，主体已匿名化。**连样例都不假装是真的。**

## 四、可复算的算法（与报告内声明、与页面逐字一致）

```
1) 找到报告里「报告指纹」那一行；
2) 把该行 `sha256:` 之后的【前 16 位】十六进制字符清空（其余全文一个字都不动）；
3) 对剩余全文按 UTF-8 编码算 SHA-256；
4) 取前 16 位十六进制 ⇒ 这就是"实算指纹"；
5) 与报告声称的值比对：相同 ⇒ 一致，不同 ⇒ FAIL。
```

三个实现细节（**都会改变结果**）：

- **必须按字节读文件**，不要先做换行转换（CRLF ↔ LF）。页面用 `readAsArrayBuffer` 就是为了这个。
- **只清空"报告指纹"那一行**。报告里还有"材料指纹"和"判据版本"两处 `sha256:`，清错了就算不对。★ 正文里引述「报告指纹字段」的句子不算那一行（它 `sha256:` 后面没有十六进制值）。
- ★ **只清前 16 位**，不要"清掉全部连续十六进制"。

### 三种结论，不是两种

| 情形 | 结论 |
|---|---|
| 声称值是 16 位十六进制，且与实算相同 | **PASS** |
| 声称值是 16 位十六进制，但与实算不同 | **FAIL** |
| 文件字节不是合法 UTF-8（如记事本另存为 ANSI / GBK） | **判不了** |
| 没有「报告指纹」行 | **判不了** |
| 「报告指纹」行里声称值是空的 | **判不了** |
| 有多行「报告指纹」 | **判不了** |
| 声称值不是 16 位（8 位 / 32 位 / 64 位） | **判不了** |

★ **FAIL 只留给「格式合规、但字对不上」。** 格式不对是**判不了**，不是 FAIL —— 否则就等于拿工具的规格去判文件的罪。（v0.1 正好犯了这个错，见 §十。）

## 五、为什么"判不了"是一等公民

因为**误报比漏报更贵**：一份报告说"这条我判不了"，你还可以去问、去查；说"这条通过了"而其实没查，你就不会再查了。

所以我们坚持三态，而不是两态：

- **红**：材料里明确缺了 / 明确有反证；
- **绿**：材料里明确满足；
- **判不了（uncomputable）**：材料没呈现、判据不适用、或需要外部证据 —— **不折算成红，也不折算成绿**。

这份样例里第三条就是"判不了"。**它敢不敢说"判不了"，是这份样例最该被检验的地方。**

## 六、外部锚（为什么需要它，怎么用）

指纹自洽 ≠ 没被改过。真正的锚在**仓库之外**：

| 锚 | 值 |
|---|---|
| `样例报告·底稿三查.md` | **`sha256:e54c748c2dde58ca`** |
| `样例报告·底稿三查·改一个字（FAIL 演示）.md` | 声称 `e54c748c2dde58ca`，**应算得 `7a903e7cb4a6cb29`** |
| `样例材料·底稿三查.txt` | **`sha256:b893302442e76faa`** |

**怎么用**：拿**这张表的值**去核你手上的文件，而不是拿文件里的值核它自己。

**再加一道**：本仓库每次发布的 **tag / commit 哈希**也是锚——README 与文件若被同时改动，tag 会暴露。本版发布为 tag **`v0.2`**。

**再再加一道（v0.2 新增）**：仓库根的 **`SHA256SUMS`** 给出每个文件的**整文件** SHA-256（64 位）。它比"报告指纹"硬，因为改正文就必须改它；但它核不了自己 —— 所以它靠 tag / commit 锚。

> **为什么仓库里有一个 `.gitattributes`**（v0.2 新增）：默认情况下，git 会把换行符在入库/检出的路上改一遍（`core.autocrlf`），
> 于是**同一次提交**在不同机器上会变成不同字节 —— 文件打开看着一模一样，`sha256sum -c` 却对不上。
> 对一个靠逐字节核指纹立身的仓库，这是致命的，而且**坏得看不出来**。
> 所以本仓库写入 `* -text`：**入库即字节，检出即字节**。你下载到的，就是校验和算过的那份。

```bash
# macOS
shasum -a 256 -c SHA256SUMS
# Linux / Git Bash
sha256sum -c SHA256SUMS
```

**核材料**（证明"报告确实是对这份材料跑的"）：

```bash
# Windows
certutil -hashfile 样例材料·底稿三查.txt SHA256
# macOS / Linux
shasum -a 256 样例材料·底稿三查.txt
```
前 16 位应等于 `b893302442e76faa`。

> §四 那张"声称 / 实算"式的对照，演示的是**自洽性**，**不构成防篡改证明**。

## 十、修订记录（v0.1 → v0.2，2026-11-01）

### 10.1 v0.1 有一个致命缺陷：页面其实一行都不执行

`复算指纹.html` 里有一句 `要防"改完再重签"`，用的是 **ASCII 直双引号**，而它落在一个**双引号字符串内部** ⇒ 整段 `<script>` **语法错误** ⇒ 页面一行不跑。

- **现象**：双击页面，静态内容全在；把报告拖进去，**什么也没发生**（判定一直是「—」）。
- **为什么一个月没人发现**：静态页看得见、源码读着全对、「算法就写在 HTML 里」也真的写着 —— **坏得看不出来**。
- **实测**（headless Chrome，拖一份样例报告进去）：

| 读数 | v0.1 | v0.2 |
|---|---|---|
| `typeof run` | `undefined` | `function` |
| 拖入后的判定 | `—`（无反应） | `PASS` |
| 控制台 | 一条未捕获异常 | 无 |

### 10.2 第二个缺陷：三态退化成两态

声称值写成 8 位 / 64 位、或文件里出现两行「报告指纹」时，v0.1 一律判 **FAIL**，并显示「不得把它当作凭证使用」——**拿工具的规格去判文件的罪**。文件字节不是 UTF-8（记事本另存为 ANSI 是最常见的一种）时，v0.1 还会误报成「没有报告指纹行，它不是本工具生成的报告」。

v0.2 把这些一律归入 **判不了**，并说明为什么判不了（表见 §四）。

### 10.3 改了什么

| 项 | v0.1 | v0.2 |
|---|---|---|
| 引号 | 整段脚本语法错，页面不跑 | 已修 |
| 判定 | PASS / FAIL（+「无声称值」） | **PASS / FAIL / 判不了**（七种情形，见 §四） |
| 非 UTF-8 | 判 FAIL 或误报「不是本工具生成的报告」 | 判不了，并提示「另存为 UTF-8 再来」 |
| 自证 | 无 | 页面底部「跑自检」：8 个已知答案的例子 |
| 外部锚 | 只有一张表 | 加 `SHA256SUMS`（整文件哈希） |
| 字节归属 | 无约束（git 可改换行） | 加 `.gitattributes` 的 `* -text`：**入库即字节** |

### 10.3b 第三个缺陷（发布前自己抓到的）：校验和与仓库字节不是同一份

`SHA256SUMS` 记的是**磁盘上那份**字节，而 git 默认会做换行转换：页面文件在磁盘上是 CRLF、入库后成了 LF。
于是**同一份提交**，我这里的哈希和从 GitHub 下载下来的哈希不相等 —— 别人跑 `sha256sum -c`，会有一条**必然 FAIL**。

这类错的恶劣之处在于**它只在别人机器上出现**：我本地一切正常，文件打开也一模一样。

修法不是"记得别用 CRLF"，而是把约束落到仓库结构上：`.gitattributes` 写 `* -text`，让 git **不再碰字节**。
判据：`git cat-file -p HEAD:<文件>` 的字节 == 磁盘字节，逐文件比对（见 §十 10.4 第 4 条）。

### 10.4 怎么核这次修订确实生效（不必相信本文）

1. 双击 `复算指纹.html` → 点「跑自检」→ 应为 **自检 8/8**；
2. 拖 `样例报告·底稿三查.md` → **PASS**；拖 FAIL 演示件 → **FAIL**；
3. 拿 `SHA256SUMS` 核文件字节；它自己不核自己，靠 tag / commit 锚；
4. 核"你下到的字节就是提交里的字节"：`git cat-file -p HEAD:SHA256SUMS` 与你手上的 `SHA256SUMS` 应逐字节相同（`.gitattributes` 就是为这条服务的）。

### 10.5 仍未做（如实）

- **大写十六进制**的声称值会被当作「不是 16 位格式」⇒ 判不了（**不会误判 PASS**，但会让人多跑一趟）；
- 未在 IE / 旧版 Edge 上验；
- 未验超大文件（10 万字以上）的读入表现；
- 本仓库的**样例报告**只有**一份**：它证明的是**机制**，不是**覆盖面**。
- 另有 `案例/` 两份（★ 见 §十一）：它们证的是**形状**，不是覆盖面。
